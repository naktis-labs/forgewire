# ADR-0001 implementation inventory

Reference: `TheStranjer/foundry-vtt-mcp` commit `c117882be3922346e4df873d6268d65ddbc68997`. This is a source inventory, not evidence that live Foundry operations work. E = exposed, P = partial, M = missing, D = intentionally restricted.

Updated after the shared-operations, connection-lifecycle and live-verification increments. Evidence is fixture-based unless stated otherwise; the rows that name a live instance were checked against a disposable Foundry VTT 14.370 instance (Node 24.22.1, D&D5e system 6.1.1, world `forgewire-test`, local storage), driven through the gateway's own REST and MCP routes.

| Persistent authenticated socket | P | P | One authenticated connection per identity serves every operation kind — world and document reads, document changes, compendium management and file browsing — with a distinct acknowledgement id per request, so concurrent requests share one socket without being confused for one another. Bounded map, idle reaper, cancellation quarantine, write deadlines, namespace-disconnect handling, redacted credential `Debug`, 64 MiB frame limit. A frame that is still queued when its request gives up — a cancelled request, or a connection invalidated while the frame was waiting — is dropped by the writer instead of being written, so a change cannot reach the instance after the request that asked for it gave up; a frame the writer already took may have reached it, and that outcome stays unknown. Evidence base: 241 workspace tests using a loopback fake Foundry (authentication fields, v13 and v14 session binding, identity resolution, interleaved ACKs, world `430` handling, cancellation and late responses, one socket shared by reads, changes, compendium management and file browsing, ambiguity when a socket drops during a change, a slow handshake that does not consume the world request budget, an upstream refusal that keeps the shared connection usable, an honored `Retry-After` hint that does not hide the upstream message, a refused session request that is not retried, a world request that waited through a broken socket and retried on the new one, a refusal that leaves a request in flight alone, a transport failure that invalidates the connection, a hint that does not carry over to a later attempt, and a change with an unknown outcome reported as possibly applied, end to end through the real connector and the REST write route, the same outcome for compendium changes, the `Retry-After` cap, the reconnect deadline, and a change refused before it reaches Foundry answering `400`, end to end through the real connector and the REST upload route, the same embedded and pack target on both transports, and an in-flight operation that keeps its target when the selection changes. The connector's cancellation and invalidation guarantees are pinned by deterministic regression tests rather than by timing: a cancelled enqueue drops its frame instead of delivering it, a cancelled change is never replayed and discards the socket, and a change on an invalidated connection is reported as possibly applied and never replayed. A frame that was enqueued but not yet written is pinned the same way: a cancelled request's queued frame never reaches the socket, an invalidated connection's queued frame never reaches the socket and the request is told the operation did not happen, and a frame the writer took keeps the unknown outcome. The application layer's failures are typed rather than matched as text — caller input, an unknown change outcome, a compendium pack that does not exist, a pack that holds another document type, and an upstream authentication refusal are distinct error types the server classifies by downcasting — and both transports resolve their target through one shared boundary that resolves the instance, takes an owned credential snapshot and enforces the credential's scope. The world's metadata allowlist is tested for the fields it exposes and for the ones it withholds (collection bodies, session state, the world's flags, author email, the compatibility object's internal flags). REST/MCP contract tests use a recording fake connector; the interoperability harness drives the real connector, including an authenticated change, against the disposable world.

Live evidence: nine checks in `crates/server/src/real_world_tests.rs` run against a disposable Foundry instance when `FORGEWIRE_REAL_WORLD_URL` is set, and are skipped otherwise. They cover world metadata over REST and MCP, all thirteen collections over both transports, single lookup by id and by name, filters, projection and byte limits, document create, change and delete over REST with an MCP read-back of the change, a create, change and delete for every one of the thirteen world-level document kinds, a create, a change and a delete for the nine embedded kinds the instance accepts with the parent document read back to prove the child hung from it, a create, a read back, a change, a read back and a delete of a document inside a compendium pack, compendium create, list and delete, a file upload and a browse that finds it, a delete of a pack the world does not advertise, by its name and by a pack id (both refused with `404` before the instance sees them), an upload into a directory the instance does not have, and the typed refusals for an unknown collection, an unknown kind, a change without data and a single read without an identifier. The checks share one world, so they take a lock and run one at a time, whether or not the test runner runs them in parallel. The documents they create carry a per-run suffix, so a run never collides with what an earlier run left behind; the compendium keeps a fixed label and is removed again, including one an earlier run left behind. `docs/interop-harness.md` records the procedure.

Independent review of this increment (the reviewer lane, over the diff from the baseline of the increment) reported two defects and three coverage gaps, all closed. A compendium delete could reach a pack the caller did not name: when the named pack published no name of its own, the delete's name was inferred from the id's shape, and the suffix of an id may be the name of a different pack — nothing is inferred from an id's shape now, and such a pack is refused. The ambiguity guard compared list occupancy instead of pack identity, so a pack whose id and name coincide was refused as ambiguous; it compares the two packs now. The connector's authentication refusals asserted only their wording, so the typed classification was not pinned end to end; the type is asserted through the connector's error context now. The cancelled-enqueue regression test did not prove the enqueue had reached the blocked hand-over, so it could pass for the wrong reason; it signals before the enqueue and proves the enqueue was still waiting for room when it was cancelled. The REST status table omitted the upstream-authentication variant; it is listed now, and two read paths that bypassed the shared classifier use it. A bounded re-review of that fix (over the fix commit alone, with a differential fuzz of the old and new name resolution) confirmed both defects closed and found one remaining low path: a pack whose published name carries surrounding whitespace resolved to the trimmed form, which another pack may publish, so the delete could reach that other pack. A padded name is refused now. The re-review also found the resolution invariant untested and the new classifier routing unpinned; a property test over a matrix of pack shapes pins that a resolved name always names the pack the caller named, and a contract test pins that a read the instance refuses keeps the upstream-authentication kind.

Outbound-writer cancellation gap (closed in this increment): the writer hands every frame it takes from its queue to the socket, and a request that gave up used to leave its frame in that queue. A mutation that was successfully enqueued but not yet transmitted could therefore still reach the instance after the request that asked for it was cancelled or its connection was invalidated: the request was gone, and the change could still be applied. Each frame now carries a shared lifecycle — the writer takes it (`Queued` to `Transmitting`) or the request that gave up takes it (`Queued` to `Cancelled`), and the first of the two wins. A cancelled frame is dropped by the writer instead of being written, and a frame the writer took may have reached the instance, so its outcome stays unknown. The same lifecycle separates the two outcomes in the errors themselves: a request whose frame never reached the socket is a definite failure (a plain upstream error, `502` without `"outcome": "possibly_applied"`), while a request whose frame was already on its way keeps the ambiguous outcome (`502` with `"outcome": "possibly_applied"`). Nothing is replayed: a cancelled frame is dropped rather than deferred, and a change is never sent twice. The regression tests are deterministic: they queue a mutation frame, hold the writer from taking it, cancel the request (or invalidate the connection) and then let the writer take the frame, with a recording socket standing in for the instance. Without the fix the writer writes the stale frame and both cancellation tests fail (`the writer must skip a frame whose request was cancelled`, `the writer must skip a frame whose connection was invalidated`).

Live findings that changed the implementation:

- Foundry's `manageCompendium` delete takes the pack's bare name, while every read identifies a pack by its id (`world.<name>`). Passing the id straight back made the live delete fail with `The requested World pack name world.<name> does not exist`. The connector resolves the name against the packs the world advertises, so the id a read reports and the pack's own name both reach the same pack, and the pack listing reports a world pack's name next to its id. A pack whose own name begins with `world.` keeps that name: among the packs the world advertises, the resolution follows the packs rather than cutting a prefix off a string. A pack the world does not advertise is refused rather than forwarded, so a delete never names a pack the caller could not have seen.
- Foundry 14 refuses `MeasuredTemplate` — a document type it deprecated — without sending an acknowledgement. The change therefore has no answer at all, and the gateway reports it the only honest way: `502` with `"outcome": "possibly_applied"`, leaving the outcome open rather than claiming the change was refused.
- The live instance stores its world data in a local key-value store rather than MongoDB, and it only serves a world while that world is launched; a restarted instance must launch the world again before any read or write answers.
- The live instance's world packs carry the bare name next to their id, but its package packs carry a name that is only unique inside their package. Reporting a package pack's name as a deletable name would reach a world pack of the same name, so the listing reports a name for world packs only.
- A document inside a compendium pack is mutated the same way a world document is: the live run creates one in a world pack, reads it back, changes it, reads it back again and deletes it, so a pack-scoped change is proven over the real protocol and not only over the fixture.
- An embedded document is updated through its parent, and the live run updates every embedded kind the instance accepts. A wall's light is an enumerated sense type (`0` none, `10` limited, `20` normal), not a boolean, so the live update sends `10`; a fixture that sent `true` or `1` would have been refused by the instance.
- The live instance publishes the name of every world pack next to its id, so a delete can resolve the pack the caller named. That was checked against the instance's own payload: a world pack is advertised with its `name` and its `id` (`world.<name>`), which is what lets the delete carry a name that names exactly one pack instead of inferring one from the id's shape.
- The world's own metadata carries more than the title and the system: the live world reports its kind (`world`), the core-version range it declares (`compatibility`), the release channel, its playtime and when it was last played. The parity review against the pinned reference added exactly those fields to the gateway's allowlist; the world's flags, relationships and session state stay out of it.

The current `FoundryClient` does not enable a reqwest cookie jar; the ADR baseline's shared-cookie-jar concern does not apply to this source. Session and connection state are isolated per identity by HMAC-keyed map entries.

Residual session-query logging risk: for Foundry 13 and earlier the WebSocket session travels in the socket.io URL query (`?session=…`), so it can appear in the Foundry server's or an intermediary proxy's access logs. Foundry 14 and later bind the session with a cookie. The gateway itself logs no passwords, cookies, or session-bearing URLs, and the credential `Debug` redacts them. The live instance is Foundry 14, so its session travels in the cookie and this risk does not apply to it.

Existing REST routes are preserved and extended: `GET /health`, `GET /api/world`, `GET /api/collections/{name}`, `POST /api/write/{operation}`, plus document, compendium, instance and file routes. MCP uses `POST /mcp`. All write paths are exercised against the disposable world only; the live run against a disposable instance of the user's own is recorded above, and no other live world was touched.
