# ADR-0001 implementation inventory

Reference: `TheStranjer/foundry-vtt-mcp` commit `c117882be3922346e4df873d6268d65ddbc68997`. This is a source inventory, not evidence that live Foundry operations work. E = exposed, P = partial, M = missing, D = intentionally restricted.

Updated after the shared-operations, connection-lifecycle and live-verification increments. Evidence is fixture-based unless stated otherwise; the rows that name a live instance were checked against a disposable Foundry VTT 14.370 instance (Node 24.22.1, D&D5e system 6.1.1, world `forgewire-test`, local storage), driven through the gateway's own REST and MCP routes.

| Persistent authenticated socket | P | P | One authenticated connection per identity serves every operation kind — world and document reads, document changes, compendium management and file browsing — with a distinct acknowledgement id per request, so concurrent requests share one socket without being confused for one another. Bounded map, idle reaper, cancellation quarantine, write deadlines, namespace-disconnect handling, redacted credential `Debug`, 64 MiB frame limit. Bounded reconnect with jitter and connection epochs apply to connection establishment, not replay of in-flight requests; a change is never replayed and reports an ambiguous outcome instead. An upstream refusal (an error acknowledgement, or an answer of an unexpected shape) fails only its own request and leaves the shared connection in use; only a transport failure invalidates the connection. An acknowledgement that carries a request's id is that request's answer even when its shape does not fit, so such an answer fails the request instead of leaving it waiting. The connection is established before the world slot is taken, so a slow handshake no longer consumes a world request's own response budget. Bounded unsolicited events are collected internally. `Retry-After` is honored for transient upstream statuses in its delta-seconds form, and an unsuccessful session GET is now terminal rather than retried. Stale-reader integration coverage remains timing-dependent. Live: every read and write in the live suite ran over the connector's persistent connection, including the compendium change and the file browse; the live suite does not count sockets, so the socket sharing itself rests on the fixture-based coverage. |

REST/MCP contract tests use a recording fake connector; the interoperability harness drives the real connector, including an authenticated change, against the disposable world.

Live evidence: eight checks in `crates/server/src/real_world_tests.rs` run against a disposable Foundry instance when `FORGEWIRE_REAL_WORLD_URL` is set, and are skipped otherwise. They cover world metadata over REST and MCP, all thirteen collections over both transports, single lookup by id and by name, filters, projection and byte limits, document create, change and delete over REST with an MCP read-back of the change, a create, change and delete for every one of the thirteen world-level document kinds, a create and a delete for the nine embedded kinds the instance accepts with the parent document read back to prove the child hung from it, compendium create, list and delete, a file upload and a browse that finds it, a delete of a pack the world does not advertise, by its name and by a pack id (both refused with `400` before the instance sees them), an upload into a directory the instance does not have, and the typed refusals for an unknown collection, an unknown kind, a change without data and a single read without an identifier. The checks share one world, so they take a lock and run one at a time, whether or not the test runner runs them in parallel. The documents they create carry a per-run suffix, so a run never collides with what an earlier run left behind; the compendium keeps a fixed label and is removed again, including one an earlier run left behind. `docs/interop-harness.md` records the procedure.

Live findings that changed the implementation:

- Foundry's `manageCompendium` delete takes the pack's bare name, while every read identifies a pack by its id (`world.<name>`). Passing the id straight back made the live delete fail with `The requested World pack name world.<name> does not exist`. The connector resolves the name against the packs the world advertises, so the id a read reports and the pack's own name both reach the same pack, and the pack listing reports a world pack's name next to its id. A pack whose own name begins with `world.` keeps that name: among the packs the world advertises, the resolution follows the packs rather than cutting a prefix off a string. A pack the world does not advertise is refused rather than forwarded, so a delete never names a pack the caller could not have seen.
- Foundry 14 refuses `MeasuredTemplate` — a document type it deprecated — without sending an acknowledgement. The change therefore has no answer at all, and the gateway reports it the only honest way: `502` with `"outcome": "possibly_applied"`, leaving the outcome open rather than claiming the change was refused.
- The live instance stores its world data in a local key-value store rather than MongoDB, and it only serves a world while that world is launched; a restarted instance must launch the world again before any read or write answers.
- The live instance's world packs carry the bare name next to their id, but its package packs carry a name that is only unique inside their package. Reporting a package pack's name as a deletable name would reach a world pack of the same name, so the listing reports a name for world packs only.

The current `FoundryClient` does not enable a reqwest cookie jar; the ADR baseline's shared-cookie-jar concern does not apply to this source. Session and connection state are isolated per identity by HMAC-keyed map entries.

Residual session-query logging risk: for Foundry 13 and earlier the WebSocket session travels in the socket.io URL query (`?session=…`), so it can appear in the Foundry server's or an intermediary proxy's access logs. Foundry 14 and later bind the session with a cookie. The gateway itself logs no passwords, cookies, or session-bearing URLs, and the credential `Debug` redacts them. The live instance is Foundry 14, so its session travels in the cookie and this risk does not apply to it.

Existing REST routes are preserved and extended: `GET /health`, `GET /api/world`, `GET /api/collections/{name}`, `POST /api/write/{operation}`, plus document, compendium, instance and file routes. MCP uses `POST /mcp`. All write paths are exercised against the disposable world only; the live run against a disposable instance of the user's own is recorded above, and no other live world was touched.
